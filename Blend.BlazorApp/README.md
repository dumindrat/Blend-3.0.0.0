# Blend Blazor Web App

The .NET 10 server-interactive Blazor app uses ASP.NET Core Identity for local account sign-in, cookie authentication, hashed passwords, lockout after repeated failed attempts, and role-based authorization. Identity data is stored in SQL Server through Entity Framework Core; the legacy user and authentication modules are not used by this login flow.

## Configure the Identity database and first administrator

Development uses SQL Server LocalDB and attaches `Blend.BlazorApp\Data\BlendIdentity.mdf`; the app applies EF Core migrations at startup. Install SQL Server Express LocalDB before running the app. For the first startup, provide a bootstrap administrator with .NET User Secrets:

```powershell
dotnet user-secrets set "Authentication:BootstrapAdmin:UserName" "admin" --project Blend.BlazorApp\Blend.BlazorApp.csproj
dotnet user-secrets set "Authentication:BootstrapAdmin:Password" "Use-a-unique-secret-of-at-least-12-characters!" --project Blend.BlazorApp\Blend.BlazorApp.csproj
dotnet user-secrets set "Authentication:BootstrapAdmin:DisplayName" "Application administrator" --project Blend.BlazorApp\Blend.BlazorApp.csproj
dotnet run --project Blend.BlazorApp\Blend.BlazorApp.csproj
```

To use a different SQL Server, override `ConnectionStrings:BlendIdentity` in User Secrets with its connection string. User Secrets are for local development, not encrypted, and stored outside the repository. Use a secret store for deployed environments; do not commit real passwords or connection credentials. The bootstrap admin must change the supplied password on first sign-in. After verifying the admin account exists, remove the bootstrap username/password settings with `dotnet user-secrets remove`, specifying each key; subsequent accounts are created by an authenticated Admin at `/Admin/Users`.

The platform `Admin` manages companies at `/Admin/Companies`; each company has a unique mapping ID from 1 to 3 for the corresponding external database, plus contact/address details, an enabled switch, and inclusive UTC subscription start/end dates. The default company maps to 1; the other two companies map to 2 and 3. The mapping range supports up to three companies. The platform Admin role remains global. Regular users can belong to multiple companies, with roles and menu items scoped to a single company; usernames remain globally unique. Existing data is migrated into a `Default Company`, and existing user-company assignments are backfilled from each user's legacy default company. Existing platform Admin users remain global. Users select their working company on `/Account/WorkingCompany`; regular users can choose among their active memberships, while platform Admins can choose any active company. The preference is saved to the account and applied at subsequent sign-ins. The working company is shown in the application header outside admin pages, and the selection page is linked from the account navigation. Disabled or expired companies cannot be selected as the working company, and signed-in users are blocked from a company that becomes inactive.

Roles and permissions are managed at `/Admin/Roles`. Platform Admins can select a company; a user with `Manage roles` can manage only their active company's roles. The built-in tenant `User` role cannot be renamed, but operation grants can be assigned to it. Administrative permissions include `Manage users`, `Manage roles`, and `Manage menu items`; company administrators receive all three by default. Users with `Manage users` can create an account or add an existing globally unique username to their active company, with a separate role assignment for that company. Editing a user's role preserves their roles in other companies. Platform Admins see all users together on `/Admin/Users`, choose a target company when adding a user, and use the per-user Companies editor to add, change, or remove company access and roles; company admins can manage only their active company. Platform Admins can select the target company on `/Admin/MenuItems`. Menu items are company-scoped, assigned from the role page, and displayed in the signed-in user's left navigation by module and group. Each company starts with a `Blend` module; company administrators can create modules such as `Stores` and assign menu items to a module from `/Admin/MenuItems`. The module selector at the top right filters workspace navigation and remembers the selection in that browser. Administrative links remain available independently of the selected module. Menu visibility grants control navigation and page access. Separately, each menu item has an operation catalog: Create, Edit, Delete, and Print are provided by default, and company administrators can add custom operations such as Approve. Role management provides per-operation grants for each role. Broker writes enforce the corresponding operation grants; other Blazor business/API operations do not yet enforce this catalog. Direct requests to configured menu paths continue to be checked against same-company menu visibility assignments; platform Admins see all entries. Operation paths must be local application paths. New accounts receive a cryptographically generated temporary password, shown only in the creation response, and must change it at first sign-in. After a role permission update, affected users must sign out and back in for the changed permission to take effect; selecting a working company refreshes the current user's company-scoped claims and saves that preference for future logins. Login uses generic credential errors and locks an account temporarily after repeated failed attempts. Account forms use antiforgery validation and secure password hashing through Identity.

## Broker directory

Users can open `/Brokers` from the left navigation when the active company's Brokers menu item is assigned to one of their roles. Platform Admins see all menu items for the active company. The page loads and searches broker records through `Blend.BusinessService` for the active working company, using that company's `CompanyNumber` (mapping ID 1, 2, or 3) as the external company mapping ID. Create and edit open a popup form. To grant a non-platform administrator write access, create a menu item with path `/Brokers` for the company, assign it to the user's role, and grant the desired Create, Edit, and Delete operations on that same role. The corresponding Add broker, Edit, and Delete buttons remain visible but disabled without their respective grants. Platform Admins can perform all three operations. Before updates and deletes, the page checks that the broker belongs to the active company; it passes the original row version to the update procedure and checks it before delete. The existing delete procedure accepts only the broker ID, so the delete check and operation are not atomic. The data service uses `ConnectionStrings:BlendData` and requires permission to execute the broker read and write stored procedures. Keep the SQL connection string in application configuration or a secret provider, not in source control. The grid displays broker code, name, contact, phone, email, and address.

The `/Buyers` menu item follows the same role-based visibility rule. The page works like the Brokers page (search, popup create/edit, delete confirmation) and uses `Blend.BusinessService.Buyers` with the active company's mapping ID. Write access uses the same rule: a menu item with path `/Buyers` assigned to the user's role, plus Create, Edit, and Delete operations granted on that role; platform Admins can do all three. The corresponding action buttons remain visible but disabled without their respective grants. As with brokers, the delete procedure accepts only the buyer ID, so its pre-check is not atomic. The grid displays buyer code, name, email, and address.

In the sidebar, Brokers, Buyers, Tea Standards and Document Numbers appear under the expandable **Master data** group for their assigned module. User administration, role management, menu items and companies appear under **Administration**, independently of the selected module. Each group contains only links the user is authorized to see and opens automatically when one of its pages is active. Other menu groups retain their existing display and configuration.

The `/TeaStandards` page opens create and edit forms in a popup and passes the active company's `CompanyNumber` mapping ID as `@CompanyId` to `trn_StandardGet`, including searches and pre-write checks, and to `trn_StandardInsert` when creating a standard. The configured database must expose a compatible read procedure accepting `@searchstr` and `@CompanyId` and an insert procedure accepting `@StandardName`, `@User`, and `@CompanyId`. The historical SQL snapshot and `DB\FixTeaStandardGetCompanyId.sql` have a single-parameter read procedure and are not compatible with this application; do not deploy the latter as a fix. The delete procedure accepts only the standard ID, so its version check and delete are not atomic.

## Data migration status

The new login intentionally replaces the legacy app login. The Broker directory is integrated with the business and data service layers; other legacy API data operations are not connected to these accounts yet. Existing .NET Framework 4.8 business/data projects and legacy API authentication remain unchanged.

Garden mark and grade services are available through the business and data service layers without a menu or page. Their legacy read and insert procedures are global and accept no company ID; callers must account for shared data across companies. The grade insert procedure ignores an existing grade, whereas garden mark insert does not deduplicate.

The `/BuyerContracts` page lists and searches contracts for the working company's mapping ID, with popup create/edit, delete confirmation, and a standards editor for adding standards and updating order quantities. Create, Edit and Delete require their corresponding Buyer Contracts operation grants; adding and updating standards requires Edit. The menu migration copies Brokers role and matching operation assignments for existing companies. The page rechecks the working company, permissions, contract version, and selected buyer or standard before writes. The legacy update and delete procedures do not enforce company ownership and header delete accepts no row version, so these checks and writes are not atomic. The legacy contract-by-ID method remains unimplemented. Standard removal is not offered by the legacy screen and the configured development database does not contain `trn_ContractDetailDelete`. Available-standard search uses the company-scoped procedure (maximum 10 search characters).

The `/DocumentNumbers` page lists document numbers for the active working company and the selected workspace module (read from the module selector's browser selection; a module named "Stores" maps to legacy module 2, every other module to Tea, module 1), via `GetDocumentDataByModule(moduleId, companyId)`. Assign the menu item and its Edit operation to a role to allow resets; platform Admins can reset without a role grant. Resets use an editor popup and a separate confirmation dialog, and recheck the selected company, permission, and record before invoking `trn_DocumentNoReset`; the legacy procedure has no concurrency token, so the check and reset are not atomic. The legacy `IncrementDocumentNo` method remains unimplemented; document-number increments used by transaction workflows must remain in the same database transaction as the associated write.
